# Lesson 03 — Project Layout: The Source Tree

By the end of this lesson you'll be able to look at any of the 36 files under
`Source/` and know, before opening it, which part of the plugin it belongs to
and roughly what it does. The project root also holds `CMakeLists.txt` (the
build recipe — lesson 04) and, after you build, a `build/` directory (which
you never edit by hand — lesson 12).

The tree looks like this:

```
DayRuinerEngine/
├── CMakeLists.txt            ← the build recipe (lesson 04)
├── learn/                    ← these lessons
├── Source/
│   ├── PluginProcessor.h/.cpp   ← the plugin itself (lesson 05)
│   ├── PluginEditor.h/.cpp      ← the GUI window (lesson 10)
│   ├── SmokeTest.cpp            ← headless DSP test (lesson 13)
│   ├── dsp/                     ← sound-making code (lessons 06, 07, 09)
│   │   ├── Grain.h
│   │   ├── GrainScheduler.h/.cpp
│   │   ├── GranularEngine.h/.cpp
│   │   ├── SampleBuffer.h/.cpp
│   │   ├── SynthEngine.h/.cpp
│   │   ├── Saturator.h/.cpp
│   │   ├── EuclideanDelay.h/.cpp
│   │   ├── LushReverb.h/.cpp
│   │   └── FFTConvolver.h/.cpp
│   ├── sequencer/               ← note-triggering code (lesson 08)
│   │   ├── TrigCondition.h
│   │   ├── ParameterLock.h/.cpp
│   │   ├── StepSequencer.h/.cpp
│   │   └── PatternManager.h/.cpp
│   └── gui/                     ← interface widgets (lesson 10)
│       ├── SequencerGrid.h/.cpp
│       ├── GrainPanel.h/.cpp
│       ├── KnobLookAndFeel.h/.cpp
│       └── ThemeManager.h/.cpp
└── build/                       ← generated by CMake; never hand-edit
```

## Why these folders exist

The split is by **rate and responsibility**:

- **`dsp/`** — code that runs on the **audio thread**, tens of thousands of
  times per second. It has the strictest rules: no memory allocation, no
  locks, no waiting, no exceptions. If DSP code breaks these rules you get
  audio glitches (clicks, dropouts). Every file here is written to obey them —
  you'll see comments like "no allocation, no locks" in the headers as a
  promise.
- **`sequencer/`** — also audio-thread code (it decides *when* notes fire),
  but separated because it's about **musical time** (steps, patterns, swing),
  not about **sound** (oscillators, filters). Keeping time-keeping apart from
  sound-making means you can reason about each one alone.
- **`gui/`** — code that runs on the **message (UI) thread**: widgets, colors,
  mouse handling. It must never do heavy work (that would freeze the window)
  and it talks to the audio thread only through lock-free mechanisms
  (atomics and the APVTS parameter system — lesson 11).

The two top-level files are the bridge: `PluginProcessor` owns the DSP and
sequencer engines and exposes them to the host; `PluginEditor` draws the
window and attaches widgets to the processor's parameters.

## Two conventions to notice now

1. **`.h` files carry the design; `.cpp` files carry the work.** The headers
   are full of comments explaining threading rules, bug-fix history, and why
   things are shaped the way they are. When you're confused, read the header
   first — it's the documentation.
2. **"BUG FIX vs sketch" comments are breadcrumbs.** Scattered through the
   code you'll find comments starting with `BUG FIX vs sketch:`. Each one
   marks a place where the original design had a real bug that code review
   caught. `DEVIATIONS.md` collects all 37 of them into one document — it's
   deliberately written as learning material.

## Check your understanding

- `Source/` has 36 files in 4 groups: top-level (processor, editor, smoke
  test), `dsp/`, `sequencer/`, `gui/`.
- `dsp/` + `sequencer/` run on the **audio thread** (no allocation, no locks);
  `gui/` runs on the **message thread**; the processor bridges them.
- Headers document the design and threading contracts — **read the `.h`
  before the `.cpp`**.
- `FFTConvolver` is compiled but unwired (a documented stub); the theme count
  is 8, not 22 (GUI design paused).
